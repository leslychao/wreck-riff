## Причины и проверка исправлений

| Наблюдение | Доказательство | Дальнейшая проверка |
|---|---|---|
| Четыре боевых паузы 62–118 мс | JFR показывает PNG-кодирование `ScreenshotAppState.postFrame` на jME3 Main; время совпадает с четырьмя capture prefixes | Автоматический camera tour ограничен smoke; benchmark/soak больше не выполняют эти захваты. Требуется повтор без tour |
| Первая загрузка 1,56 с | `ArenaFactory.build -> SurfaceMaterials.texture -> AWTLoader`: распаковка и преобразование 16-bit PNG | Проверить подготовку эквивалентных runtime-текстур и повторить cold load |
| Большой объём временных объектов | `CombatVisuals.renderFields`: повторный `HashSet<Long>`, boxing соседей и коллизии `Long.hashCode` | Кеширование геометрии и масок краёв по сроку жизни огненной поверхности; повторный JFR |
| Ранний кадр около 87 мс | В близком временном окне есть три native sample компиляции/линковки шейдера | Привязка к конкретному кадру приблизительна; нужны отдельные замеры первого использования |

GC не объясняет большие боевые паузы: обычные остановки менее 5 мс.
Full GC 13–14 мс вызван диагностикой после выгрузки матча. Внешний `jcmd Thread.print`
на 40-й секунде занял около 0,28 мс и произошёл после четырёх PNG-пауз.
Профилирование и захваты влияют на сценарий; после исправлений обязательны
сопоставимый короткий профиль и окончательные шесть benchmark без `--profile`.

Предыдущий 110-секундный soak завершился по тайм-ауту. Новый короткий запуск его
не повторил, но причинную связь с какой-либо одной правкой не устанавливает.

Изменения в этом сравнении: runtime diffuse PNG подготовлены в 8-bit с точным
совпадением результирующих пикселей штатного AWTLoader; готовая геометрия огня
кешируется по сроку жизни; автоматические PNG camera tour исключены из soak.
Последнее устраняет влияние диагностических захватов на измерение. Оно само по себе
не доказывает устранение обычного игрового фриза. Частота отрисовки не ограничена,
поэтому общий расход памяти в секунду нужно сопоставлять также с числом кадров.

Оставшийся drop относится к первому боевому update после TRANSITION 100,248 мс
на tick 0. Проверка кода выявила, что завершение MatchLoading сразу включает
RUNNING: новый SimulationLoop получает длительность предшествующего loading-кадра,
а следующий update — стоимость первого полностью подготовленного изображения.
Требуется отдельная проверка границы готовности изображения и игрового времени;
реальные последующие боевые задержки должны продолжать учитываться полностью.
Этот короткий профиль по-прежнему не закрывает итоговый gate шести карт/600 с и
30-минутную проверку ресурсов окончательного ZIP.

## Повтор после исправления границы загрузки

`build/soak-loading-check-20260913`, PID 7948, source
`ce05e299069e3238256dd36dfaf617373bc595233a569bb463269c96eb37301a`:
запуск с прежними аргументами, но без `--profile`, завершился EXIT 0.
Три загрузки, два Retry, errors=[], undrawableSeconds=0, droppedSimulationSeconds=0.
В бою 60 681 кадр за 65,765 с: p95 1,75 мс, p99 2,35 мс, максимум 47,919 мс,
кадров >50 мс нет. Загрузка учитывается отдельно: максимум 893,459 мс.

MatchLoading теперь подтверждает реальную отрисовку готовой сцены до публикации
RUNNING. Время завершённого loading-кадра не передаётся в новый SimulationLoop.
Тест с последующим настоящим боевым кадром 200 мс сохраняет 12 ticks и 100 мс drop;
метрики не фильтруют медленный бой. Это подтверждает исправление границы времени.
Изменение p95/p99 здесь нельзя приписать только этой правке: подробное
профилирование также выключено. Остаток почти 0,9 с в одном loading-кадре
требует разбиения синхронного декодирования через существующие стадии загрузки.

## Повтор после поэтапного декодирования

`eeba3db5855d16ba1d7f40514227543bf90b81949b2f4875f09fd0d1b094b504`:
тот же 70-секундный сценарий без `--profile`, EXIT 0, три загрузки и два Retry.
По одной текстуре за update через существующий AssetManager; рецепты материалов
одни для планирования и сборки, временные ссылки освобождаются после сборки,
ошибки или отмены. Native-проверка всех шести арен сравнивает фактические ключи
и identity декодированных Image, без дублирующего списка ассетов.

В бою 62 787 кадров за 65,441 с: p95 1,75 мс, p99 2,35 мс, максимум 47,692 мс,
кадров >50 мс нет. droppedSimulationSeconds=0, errors=[], undrawableSeconds=0,

Сборка окружения и первый вывод материалов остаются синхронными операциями
потока владельца. Этот короткий результат подтверждает разбиение декодирования,
но не заменяет шесть полных benchmark и 30-минутный soak окончательного ZIP.
